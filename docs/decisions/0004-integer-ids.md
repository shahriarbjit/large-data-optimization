# 0004: Integer IDs for now

- **Status:** Accepted
- **Date:** 2026-11-16

## Context

Every resource needs an ID in URLs and JSON. The choice affects database indexes, URLs, and what an ID reveals to a client.

## Options

1. **Auto-increment integers.** Smallest and fastest indexes, readable in support conversations ("order 1042"). They reveal counts and order and are guessable, so authorization must never rely on secrecy.
2. **UUID (v7) or ULID.** Not guessable, can be generated by clients and in other services, and time-ordered, so indexes stay reasonable. Larger and harder to read aloud.

## Decision

Integers for now:
- JSON `id` fields are integers.
- Route parameters are constrained to digits (`whereNumber`), so `/orders/abc` is a 404.

## Reason

- The application is a single database monolith; we have no need for distributed ID generation yet.
- Every endpoint will be protected by Policies, so a guessable ID gives no access.
- Integer IDs are simpler for the first features.

## Consequences

- Revisit this decision before the first public, unauthenticated resource URL, before extracting a module into a service, or before merging data from several databases.
- Changing to UUIDs later means a new column, a migration period and an `/api/v2` if the type in JSON changes. Do it per resource, not all at once.
- Request IDs (`X-Request-Id`) and idempotency keys already use UUIDs or ULIDs; that is independent of resource IDs.
